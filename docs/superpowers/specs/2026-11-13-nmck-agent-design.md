# Агент обоснования НМЦК — проектный документ

Дата: 2026-11-13
Статус: черновик на согласование

## 1. Зачем и для кого

Хакатон, задача 2 «Обоснование начальной максимальной цены договора» (описание и критерии — `docs/Описание кейса для участников.docx`, источники — `docs/Список источников.docx`, примеры ТЗ — `docs/ТЗ *.docx`).

Пользователь — сотрудник закупок МФТИ. Он загружает техническое задание, а система сама ищет сопоставимые предложения в открытых источниках, отбирает релевантные, приводит цены к сопоставимому виду, исключает аномалии и считает НМЦК. Результат — отчёт, по которому можно восстановить путь от ТЗ до итоговой цены.

Продукт задуман как **внутренний инструмент МФТИ, работающий локально** на компьютере пользователя: своего сервера нет. Это упрощает разработку, оставляет OpenRouter-ключ у пользователя, а запросы к маркетплейсам идут с обычного (не дата-центрового) IP, что снижает блокировки.

Цель команды на хакатоне — пройти в топ-3 по техническим критериям (100 баллов) и сильно выступить на защите (отраслевые, 30 баллов). Важнее всего по весу: поиск (20), сопоставимость и нормализация (20), развертываемость (20), расчёт и аномалии (16).

## 2. Цели, не-цели, анти-цели

**Цели**
- Основной сценарий от загрузки ТЗ до готового отчёта работает на трёх примерах ТЗ (бумага, 3D-принтер, цитокины) и на новых категориях.
- Интерфейс — чат с ИИ-агентом и отчёт сбоку; агент задаёт уточняющие вопросы по ходу, пользователь может попросить скорректировать результат.
- Если источнику нужен вход в аккаунт или капча — пользователь проходит их сам в живом окне браузера внутри интерфейса.
- Запуск одной командой `docker compose up` в чистом окружении.
- Дизайн — минималистичный, белый, «дорогой» (вёрстка через скиллы impeccable и anthropic frontend; макеты команда делает отдельно).

**Не-цели (сейчас)**
- Свой сервер, многопользовательский режим, авторизация пользователей.
- Установщик для неподготовленного пользователя (только Docker).
- Локальная LLM для персональных данных — в кейсе их нет; уходит в план развития.
- Журнал действий внутри отчёта — вместо него версии отчёта в интерфейсе.

**Анти-цели (провал, даже если «работает»)**
- Итоговая цена посчитана LLM «в тексте» и не воспроизводится.
- Система выдаёт цену при недостатке данных вместо явного предупреждения.
- Предложение в отчёте без ссылки на источник.
- Сопоставление только по названию, без существенных характеристик.

## 3. Ограничения

- Через внешние API можно передавать только открытые данные (ТЗ в кейсе — открытые).
- LLM-провайдер — OpenRouter (ключ в настройках).
- Обязательны: Dockerfile + Docker Compose, README (требования, запуск/остановка, зависимости, переменные окружения, внешние сервисы), описание архитектуры и потока данных, ≥ 2 use case с примером входа и ожидаемого результата.
- Методическая база расчёта — метод сопоставимых рыночных цен (Методические рекомендации Минэкономразвития, приказ № 567): НМЦК как среднее по выборке, однородность при коэффициенте вариации ≤ 33 %, не менее 3 цен от разных поставщиков, приведение цен прошлых периодов через индексы потребительских цен. *Команде стоит сверить с актуальной редакцией.*
- Приказ № 567 обязателен для закупок по 44-ФЗ. МФТИ, вероятно, закупает по 223-ФЗ, где порядок определения цены задаёт положение о закупке заказчика. Поэтому в отчёте методика названа прямо: «метод сопоставимых рыночных цен, формулы по аналогии с приказом № 567», а текст этой оговорки и все пороги лежат в конфиге и меняются под положение МФТИ без правки кода. *Команде стоит уточнить у организаторов, по какому закону и положению работает заказчик.*

## 4. Рассмотренные подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| A | Десктоп-приложение (Electron) со встроенным браузером | Лучше всего обходит антибот, удобный вход в аккаунты | Плохо упаковывается в Docker (теряем часть из 20 баллов), сложнее дать жюри протестировать |
| **B** | **Веб-интерфейс + локальный бэкенд в Docker с управляемым Chromium и живым окном браузера в UI** | Вся ценность A (чат, отчёт, вход/капча руками) + Docker одной командой | Нужно транслировать вкладку браузера в UI |
| C | Пошаговый мастер-конвейер, чат вторичен | Самый предсказуемый, ближе всего к критериям | Меньше «вау» на защите |

**Выбран B.** Внутри в любом случае детерминированный конвейер (идея C), а чат — интерфейс поверх него.

## 5. Решения

### 5.1 Запуск и состав

- `docker compose up` на машине пользователя → открыть `http://localhost:<порт>` в обычном браузере.
- Фронтенд: React (Vite). Бэкенд: Python, FastAPI. Chromium под управлением Playwright — внутри контейнера бэкенда. *(выбор стека — наш, по умолчанию)*
- Хранилище: SQLite + файлы в Docker-томе (закупки, версии отчётов, настройки, конфиг источников). Профиль браузера (cookies, входы) — тоже в томе, входить нужно один раз.
- Живое окно браузера: трансляция вкладки контейнерного Chromium в UI (например, через CDP screencast) с передачей кликов и ввода. Появляется, когда источнику нужен вход/капча, а также по запросу пользователя.

### 5.2 Конвейер

```
ТЗ (.docx / .pdf / текст)
 → разбор: позиции, ед. изм., кол-во, ОКПД2, характеристики (существенные / второстепенные)
 → уточняющие вопросы (единицы, фасовка, «или эквивалент», неоднозначности)
 → поиск по источникам (адаптеры)
 → извлечение предложения: ссылка, дата получения, цена, ед. изм., характеристики
 → сопоставление с ТЗ: релевантность + причина включения/исключения; удаление дублей
 → приведение цены: к единице ТЗ → НДС → индексация старых цен → доставка
 → одна цена от одного поставщика
 → расчёт: выбросы, статистика, НМЦК по позициям и итог; при нехватке или неоднородности данных — предупреждение с возможной причиной разброса
 → отчёт (из структурированных данных) + экспорт
```

- **Многопозиционные ТЗ** (бумага — 3 позиции, цитокины — 5): НМЦК считается по каждой позиции (цена за единицу × количество), затем суммируется.
- **Уточняющие вопросы** задаются в чате. Пока ждём ответа по одной позиции, работа по остальным продолжается. *(наше решение)*
- **Работа без участия человека.** Жюри будет запускать систему у себя со своим ключом OpenRouter и, возможно, не захочет проходить капчи. Поэтому основной сценарий доходит до отчёта и без человека: у каждого уточняющего вопроса есть предлагаемый ответ по умолчанию, который агент использует и явно отмечает в отчёте, если ответа нет; источник с капчей/входом без реакции пользователя пропускается со статусом «требует входа». Живое окно и вопросы улучшают результат, но не блокируют его. *(наше решение)*
- **Товары, работы, услуги.** Модель данных не предполагает фасовок и маркетплейсов: единица измерения произвольная (шт., пачка, мкг, час, м², услуга). Для работ и услуг основной источник — контракты ЕИС и открытый веб. Демонстрационные примеры — товары. *(наше решение)*

### 5.3 Разделение LLM и кода

LLM **извлекает и сравнивает**, код **вычисляет**.

- LLM: разбор ТЗ в структуру, генерация поисковых запросов, извлечение полей со страницы (цена, фасовка, характеристики), оценка соответствия характеристик ТЗ с объяснением, ведение диалога.
- Условия предложения сохраняются как поля: дата цены, НДС, поставщик (название, ИНН, если есть), доставка. LLM только записывает то, что написано на странице; поправки считает код (см. 5.3.1).
- **Доставка — условие предложения, а не сумма.** *(наше решение)* Все три ТЗ требуют цену «с включением всех дорожных, транспортных и иных расходов», но точная стоимость доставки на большинстве сайтов видна только в корзине после ввода адреса или входа. До оформления заказа система **не доходит никогда**. Вместо этого:
  1. С карточки товара LLM берёт только то, что там написано: «доставка бесплатно / включена», порог бесплатной доставки («бесплатно от 5 000 ₽»), явную сумму доставки.
  2. Для источника в конфиге можно задать условия доставки для юрлиц в Московской области (включена всегда / бесплатно от суммы N ₽) — заполняются один раз со страницы условий доставки. Для ЕИС задано «включена»: цена контракта по 44-ФЗ, как правило, включает доставку до заказчика; в отчёте это видно как допущение.
  3. Код решает по каждому предложению: условия со страницы важнее условий источника; если сумма заказа по ТЗ (цена за единицу × количество) не меньше порога — доставка включена; если на странице указана сумма доставки — она распределяется на **весь объём по ТЗ** (сумма / количество), а не на фасовку из предложения; иначе — «неизвестно», без поправки.
  4. Процентная надбавка «на глаз» не применяется: её нечем обосновать.
  5. В отчёте у каждого предложения видно условие доставки и откуда оно взято; в расчёте — сколько предложений с подтверждённой и неизвестной доставкой; в предупреждениях — позиции, где доставка не подтверждена, и дополнительные требования ТЗ (разгрузка, занос), которые найденные цены не отражают.
- Код (детерминированно): приведение к единице ТЗ (например, упаковка 5 пачек за 1 450 ₽ → 290 ₽/пачка; цена за мкг для цитокинов), поправки на НДС, дату и доставку, отбор одной цены от поставщика, правило выбросов, среднее/мин/макс/СКО/коэффициент вариации, НМЦК по позициям и итог. Одна и та же выборка всегда даёт одну и ту же цену; формулы показываются в отчёте.

#### 5.3.1 Приведение цены к сопоставимому виду *(наше решение, параметры в конфиге)*

Расчётная цена предложения считается кодом по одной формуле, и каждый множитель виден в отчёте:

```
расчётная цена = цена за единицу ТЗ × коэффициент НДС × коэффициент индексации + доставка на единицу
```

**НДС.** Все цены приводятся к виду «с НДС»: это сумма, которую заказчик реально платит. Устроено так же, как доставка: страница важнее настроек источника, догадок нет.

| Что известно о цене | Что делает код |
|---|---|
| с НДС | без поправки |
| без НДС, налог начисляется сверху | × (1 + ставка); ставка со страницы, иначе из конфига (по умолчанию 22 % — ставка с 01.01.2026; *сверить*) |
| НДС не облагается (поставщик на упрощённой системе) | без поправки: это конечная цена |
| на странице не сказано | берётся значение по умолчанию для источника: ЕИС — «с НДС» (цена контракта конечная), розничные магазины и маркетплейсы — «с НДС»; каталоги поставщиков — «неизвестно», без поправки |

Предложения с неизвестным НДС остаются в выборке; в расчёте видно их число, в предупреждениях — что цена по ним может быть занижена.

**Индексация цен прошлых периодов.** Цена старше 6 месяцев (порог в конфиге) умножается на коэффициент по формуле из приказа № 567 (*п. 3.18, сверить*):

```
k = (100 + Σ (ИПЦ месяца − 100)) / 100
```

Сумма берётся по месяцам от следующего за месяцем цены до месяца, предшествующего расчёту. ИПЦ — месячные индексы потребительских цен Росстата, в процентах к предыдущему месяцу; таблица лежит в конфиге (`cpi.yaml`) и обновляется без правки кода. Если за часть месяцев данных нет, коэффициент считается по имеющимся, и это написано у предложения. Дата расчёта сохраняется в отчёте, поэтому пересчёт той же версии даёт ту же цену. Цены с сайтов без указанной даты считаются текущими. Индексацию можно выключить в конфиге.

**Одна цена от одного поставщика.** Несколько контрактов или карточек одного продавца не являются независимыми ценами. Поставщик определяется по ИНН; если его нет — по названию; для обычных интернет-магазинов — по домену сайта. На маркетплейсах поставщик — продавец, а не площадка; если продавец не указан, предложения считаются независимыми. Из цен одного поставщика в расчёт идёт самая свежая (при равных датах — меньшая), остальные уходят в исключённые с причиной «повторная цена того же поставщика» и ссылкой на оставленную. Пользователь может вернуть такую цену через чат.

Порядок шагов фиксирован: приведение → отбор по поставщику → выбросы → статистика.

### 5.4 Источники

Каждый источник — отдельный адаптер с общим интерфейсом «запрос → список предложений + статус». Набор и параметры источников задаются в конфиге, без переделки основной логики.

**Каскад источников (решение команды).** Цены собираются по уровням, следующий уровень подключается только при нехватке данных. Решение принимается по каждой позиции отдельно:

1. **Уровень 1:** **ЕИС Закупки** (реестр контрактов: исполненные, последние 3 года; главный источник) + **каталоги производителей и дистрибьюторов** в открытом вебе (для цитокинов и 3D-принтеров это профильные поставщики) + ГИСП/ЭТП, если доступны.
2. **Уровень 2:** **маркетплейсы и интернет-магазины** (Яндекс Маркет, Ozon, ВсеИнструменты, Комус) и агрегаторы (Берёзка, Портал поставщиков). Подключаются, если после исключения выбросов на уровне 1 осталось меньше 3 релевантных цен **или выборка неоднородна** (коэффициент вариации выше порога): приказ № 567 в этом случае рекомендует расширять выборку, а не отказываться от расчёта. Маркетплейсы работают через браузер; при капче или входе открывается живое окно.

Если уровень 2 подключён, цены обоих уровней объединяются в одну выборку для расчёта. В разделе «Где искали» видно, какие уровни задействованы и почему. Порог перехода (3 цены) задаётся в конфиге.

Устойчивость: недоступный источник, сменившаяся вёрстка, отсутствие полей, сетевые ошибки не обрывают поиск; статус каждого источника фиксируется и попадает в отчёт.

### 5.5 Правила и их редактирование агентом

- Правила сопоставления и расчёта (порог коэффициента вариации, правило выбросов, минимальное число цен, глубина поиска по ЕИС и т. п.) лежат в конфиге рядом с источниками.
- Пользователь может менять конфиг **через агента** («добавь сайт X», «выбросом считай отклонение больше 25 %»). Агент показывает изменение и применяет его после подтверждения. *(наше решение: тихая правка правил незаметно меняет расчёт)*
- Также доступна страница настроек источников и правил в UI.

### 5.6 Правило выбросов *(наше решение, параметры в конфиге)*

- n ≥ 5: исключаются цены за пределами [Q1 − 1,5·IQR; Q3 + 1,5·IQR].
- n < 5: исключаются цены, отклоняющиеся от медианы более чем на 50 %.
- После исключения: если цен < 3 или коэффициент вариации > 33 % — НМЦК по позиции помечается как необоснованная, отчёт явно говорит о недостатке/неоднородности данных и предлагает действия (расширить поиск, уточнить требования). Цена при этом может быть показана справочно, но не как итог.
- **Подсказка о причине разброса.** Если выборка осталась неоднородной и после уровня 2, код сравнивает средние цены в парах групп: ЕИС и остальные источники; НДС подтверждён и неизвестен; цена проиндексирована и нет; доставка подтверждена и неизвестна. Если средние различаются больше чем на 15 % (порог в конфиге), в предупреждение попадает подсказка, например «цены ЕИС в среднем на 28 % ниже остальных (4 против 3 предложений)». Система сама выборку под нужную вариацию не сужает: это подгонка результата. Решение — за пользователем, через чат («оставь только ЕИС», «исключи это предложение»).

### 5.7 Содержание отчёта (вид — позже, делает команда)

1. **Предмет закупки** — позиции из ТЗ, существенные характеристики.
2. **Где искали** — источники, запросы, дата, статус по каждому (найдено / пусто / недоступен).
3. **Включённые предложения** — источник, поставщик, ссылка, дата получения, дата цены, исходная цена и единица, цепочка приведения (цена за единицу ТЗ → НДС → индексация → доставка → расчётная цена) с основанием каждой поправки, сравнение характеристик с ТЗ, причина включения.
4. **Исключённые предложения** — с причиной (аномальная цена, несопоставимая комплектация, неподходящая единица, недостаток данных, дубль, повторная цена того же поставщика).
5. **Расчёт** — методика и оговорка о её применимости, дата расчёта, правило выбросов, число цен, мин/макс, среднее, коэффициент вариации, НДС (с НДС / начислен / неизвестен — сколько предложений), индексация (сколько цен проиндексировано), доставка (включена / добавлена / неизвестна — сколько предложений), НМЦК по позициям и итог.
6. **Предупреждения** — например «по позиции 3 найдено 2 цены, обоснование недостаточно», «по позиции 2 выборка неоднородна (CV = 41 %); цены ЕИС в среднем на 28 % ниже остальных», «по позиции 1 НДС не подтверждён у 2 из 7 предложений», «по позиции 1 доставка не подтверждена у 4 из 7 предложений — цена может быть занижена», «требования ТЗ о разгрузке и заносе в найденных ценах не отражены».

Связь цены с источником — как минимум ссылкой. Нужны ли дополнительные доказательства (скриншоты, сохранённые копии страниц), решается вместе с видом отчёта.

Экспорт: DOCX и/или PDF. *(формат — на усмотрение команды при проектировании вида отчёта)*

### 5.8 Интерфейс (функционально; макеты — отдельно)

- **Список закупок** — прошлые исследования, создание новой (загрузка ТЗ).
- **Экран закупки** — чат с агентом + панель отчёта сбоку; прогресс поиска виден в чате.
- **Версии отчёта** — каждое изменение данных (ответ на уточнение, исключение предложения, правка правил, повторный расчёт) создаёт новую версию; в панели отчёта можно переключаться между версиями.
- **Живое окно браузера** — для входа/капчи или по запросу.
- **Настройки** — OpenRouter-ключ, выбор модели; источники и правила.

Правки через чат («исключи это предложение», «считай за мкг») меняют структурированные данные → пересчёт → новая версия отчёта. Отчёт не переписывается текстом.

## 7. Use cases для README

1. **Бумага** (`ТЗ поставка бумаги.docx`): 3 позиции, конкретная марка SvetoCopy, много источников (ЕИС, Комус, маркетплейсы). Ожидается: по каждой позиции ≥ 3 цены за пачку, нормализация упаковок, НМЦК по позициям и итог.
2. **Цитокины** (`ТЗ поставка цитокинов.docx`): нишевые реагенты, «1 шт. = не менее 10/100 мкг», фасовки у поставщиков разные. Ожидается: уточняющий вопрос о единице сравнения, нормализация по массе, проверка существенных характеристик (чистота, эндотоксин, клеточная линия), честное предупреждение там, где данных мало.
3. *(дополнительно)* **3D-принтер** (`ТЗ поставка 3D принтер.docx`): одна конкретная модель; ЕИС-контракты и дистрибьюторы.
