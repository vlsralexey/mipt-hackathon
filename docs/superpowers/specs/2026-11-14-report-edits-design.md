# Изменение отчёта по просьбам пользователя — проектный документ

Дата: 2026-11-14
Статус: черновик на согласование
Основа: `docs/superpowers/specs/2026-11-13-nmck-agent-design.md` (§5.5, §5.6, §5.8), план `docs/superpowers/plans/2026-11-13-nmck-backend-p0.md` (Tasks 1, 10–14).

Пометка *(наше решение)* — выбор, сделанный при проработке; его можно оспорить.

## 1. Зачем

Первый прогон агента почти никогда не окончательный. LLM ошибается при разборе страницы (не увидела «с НДС», перепутала фасовку), сопоставление отбрасывает подходящее предложение, источников не хватает, у сотрудника закупок есть своё знание о рынке. Всё это пользователь исправляет словами в чате: спрашивает «почему», просит исключить, поправить, поискать ещё, поменять правило.

Документ описывает, о чём пользователь может просить, во что превращается каждая просьба и как это реализовать, чтобы:
- любая цена в отчёте по-прежнему считалась кодом и восстанавливалась по данным;
- любое изменение было видно в отчёте с причиной и отменялось;
- агент не мог «нарисовать» нужную цену ни по своей инициативе, ни по просьбе.

## 2. Цели, не-цели, анти-цели

**Цели**
- Агент отвечает на вопросы об отчёте по данным, без новой версии.
- Правки выборки, предложений, позиций и правил меняют структурированные данные → пересчёт кодом → новая версия.
- Ручные правки переживают повторный поиск.
- В отчёте есть раздел «Правки пользователя»; каждую правку можно отменить.
- Кнопки в чате и отчёте (ответ на вопрос, «Пропустить источник», «Отменить», «Применить») идут тем же путём, что и просьбы словами, но без LLM.
- Две области настроек (решение команды 2026-11-14):
  - **общие** — конфиг источников и правил на странице «Настройки»; внизу страницы поле, где агенту пишут, что поменять (§5.8);
  - **локальные** — правила и источники одной закупки; меняются из её чата и действуют только на неё (§5.5).

**Не-цели**
- Свободная правка текста отчёта.
- Позиции, которых нет в ТЗ: новое ТЗ — новая закупка.
- Правка общих настроек из чата закупки и локальных — со страницы «Настройки»: у каждой области своё место.

**Анти-цели (провал, даже если «работает»)**
- Число в отчёте или в ответе агента, которое не посчитал код.
- Агент сам сужает выборку под нужную цену или коэффициент вариации.
- Правка без причины или без следа в отчёте.
- Цена в расчёте без источника (ссылки или файла).
- Изменение, которое пользователь не заметил.

## 3. Принципы

1. **Поиск — данные, просьба — правка.** Найденные предложения хранятся как есть. Просьба пользователя сохраняется отдельной записью — правкой. Отчёт = результаты поиска + действующие правки, собранные кодом.
2. **LLM — только при создании правки.** Если правке нужна LLM (ответ на уточняющий вопрос меняет позицию; разбор страницы по ссылке пользователя), её результат сохраняется в правке или в результатах поиска. Сборка отчёта — чистый код без сети и LLM: одни и те же данные и правки всегда дают ту же цену.
3. **Агент не считает.** Любое число в ответе агента берётся из результата инструмента. Сводку «итог 793 990 → 776 790 ₽» после правки формирует код (§6.7).
4. **Однозначная просьба — уже подтверждение.** «Исключи контракт 3810» выполняется сразу и отменяется одной кнопкой. Подтверждение нужно, когда понимание агента может разойтись с намерением человека: правила, массовые исключения по признаку, откат нескольких правок, действия, которые предложил сам агент (§6.4).
5. **У правки всегда есть причина.** Слова пользователя или их краткий пересказ; причина попадает в отчёт.

## 4. Рассмотренные подходы

| | Подход | Плюсы | Минусы |
|---|---|---|---|
| A | Правки внутри отчёта (`overrides` в `PositionReport`, как в плане) | Меньше переделок | Повторный поиск перезаписывает позицию и теряет правки; исправление поля затирает исходное значение; отменить одну правку нельзя |
| **B** | **Отдельный список правок поверх результатов поиска; отчёт каждый раз собирается заново** | Правки переживают повторный поиск, видны и отменяются по одной; исходные данные со страницы не теряются | Новые таблицы и функция сборки (но `recalculate_position` из плана — почти она) |
| C | Одно универсальное действие «изменить отчёт»: агент присылает изменения полей | Гибко, мало инструментов | Модель может вписать число напрямую — нарушение «считает код»; трудно проверять |

**Выбран B** (согласовано с командой 2026-11-14).

## 5. О чём просит пользователь

Каталог — это и требования к агенту, и набор фраз для проверки (§12). Коды (В1, П2 …) используются в остальных разделах.

### 5.1 Вопросы — без новой версии

| # | Примеры | Что делает агент |
|---|---|---|
| В1 | «Откуда 310,98?», «Как посчитан итог?» | `get_position`: среднее по N ценам, правило выбросов, CV, формула итога |
| В2 | «Почему исключили контракт 3810?», «Почему Регион в расчёте?» | `get_offer`: причина исключения или включения, сравнение характеристик |
| В3 | «Почему у Региона 290, а на сайте 1 450?» | `get_offer`: цепочка приведения (фасовка → НДС → индексация → доставка) с основанием каждого шага |
| В4 | «Искал на Комусе?», «Что с ГИСП?» | `get_sources`: статусы, запросы, сколько найдено |
| В5 | «Что такое коэффициент вариации?», «Почему нужно 3 цены?», «По какому закону считаем?» | Объяснение; пороги — из действующих правил закупки, методика — из `Report.methodology` |
| В6 | «Что изменилось с версии 2?» | `diff_versions` |
| В7 | «Что сейчас делаешь?», «Долго ещё?» | Состояние прогона: какие позиции и источники в работе |
| В8 | «Что делать с позицией 3?» | Предлагает действия по предупреждениям и `spread_hints` (поискать ещё, проверить предложения с неизвестным НДС). **Сам не выполняет**: согласие пользователя превращает предложение в просьбу из §5.2–5.5 |

### 5.2 Правки выборки

| # | Примеры | Правка | Подтверждение |
|---|---|---|---|
| П1 | «Исключи контракт 3810, там б/у» | `exclude` | нет |
| П2 | «Оставь по позиции 2 только ЕИС», «Убери маркетплейсы», «Исключи цены старше 2025 года» | `exclude_where` (фильтр) | да, с предпросмотром |

| П4 | «У Северной бумаги цена с НДС», «В коробке 10 пачек, а не 5», «Это контракт 2025 года», «Это один и тот же поставщик» | `correct_offer` (поле → значение) | нет |
| П5 | «Добавь это предложение: <ссылка>» | `add_offer`: страница загружается и разбирается при создании правки | нет |

| П7 | «Возьми цену 300 ₽ у ООО „Ромашка“» — без ссылки и файла | Отказ: цена без источника в расчёт не идёт; агент просит ссылку или файл | — |

**Что можно вернуть (П3).** *(наше решение)*

| Причина исключения | Можно вернуть? |
|---|---|
| `incomparable`, `insufficient_data`, `same_supplier` | Да. Предложение идёт в выборку в обход проверки и отбора по поставщику, в отчёте — «возвращено пользователем: <причина>» |
| `anomalous_price` | Нет. Выброс определяется правилом по всей выборке. Агент объясняет правило и может предложить изменить его (§5.5) |
| `unit_mismatch` | Нет, пока не исправлена фасовка или единица (П4); после исправления предложение пересчитается само |

| `user_excluded` | Это отмена правки `exclude` (`cancel_edit`), а не новая `include` |

**Фильтр П2 — это условие, а не список.** Если повторный поиск найдёт новые предложения с маркетплейсов, «убери маркетплейсы» исключит и их. В предпросмотре — какие предложения затронуты сейчас и как изменится расчёт.

### 5.5 Локальные настройки закупки

Закупка работает по общим настройкам (§5.8), но в её чате можно поменять правила и источники только для неё. Например, для одной закупки нужен порог разброса 40 %, а для нишевого реагента — сайт конкретного дистрибьютора. Каждое такое изменение — правка `local_setting`; общие настройки и другие закупки оно не трогает.

| # | Примеры | Локальная настройка | Когда действует |
|---|---|---|---|
| Пр1 | «Выбросом считай отклонение больше 25 %» | `rules.median_max_deviation = 0.25` | Сразу: пересчёт |
| Пр2 | «Порог разброса 20 %», «Минимум 5 цен» | `rules.cv_threshold`, `rules.min_prices` | Сразу |
| Пр3 | «Не индексируй цены», «Ставка НДС 20 %» | `rules.indexation_enabled`, `rules.vat_rate` | Сразу |
| Пр4 | «Маркетплейсы подключай только при нехватке цен», «Ищи в ЕИС за 5 лет» | `rules.level2_on_heterogeneous`, `rules.eis_years` | На следующих поисках |
| Пр5 | «Не учитывай Ozon», «Не ищи на маркетплейсах» | `sources.<id>.enabled = false` или сайт убран из `sources.<id>.sites` | Сразу: найденные там предложения исключаются с причиной «источник отключён в настройках закупки»; в следующих поисках источник не участвует |
| Пр6 | «В этой закупке ищи ещё на sigmaaldrich.com» | сайт добавлен в `sources.<id>.sites` | На следующих поисках; агент предлагает сразу поискать (С2) |
| Пр7 | «Пересчитай по новым общим настройкам» | База закупки обновляется до текущих общих настроек (§6.1); локальные остаются поверх | Сразу |

- Всегда с подтверждением и предпросмотром. В карточке прямо написано «для этой закупки».
- Менять можно только ключи из белого списка. Правила: `min_prices`, `cv_threshold`, `iqr_k`, `iqr_min_n`, `median_max_deviation`, `vat_rate`, `indexation_enabled`, `index_after_months`, `level2_trigger_min_prices`, `level2_on_heterogeneous`, `eis_years`. Источники: `enabled`, `sites`. Текст методики, `marketplace_hosts`, условия НДС и доставки источников — только в общих настройках.
- Значения, мягче методических рекомендаций (`cv_threshold` > 0,33, `min_prices` < 3), допустимы — положение о закупке по 223-ФЗ может это разрешать, — но в отчёт попадает предупреждение: «Порог однородности 40 % мягче методических рекомендаций (33 %)». *(наше решение)*
- Если просьба неоднозначна (Пр1: «отклонение 25 %» подходит и к правилу медианы, и к коридору межквартильного размаха), агент в карточке подтверждения прямо пишет, какое правило меняет.
- Все действующие настройки закупки видны на вкладке «Локальные настройки» правой панели; у изменённых — кнопка «Сбросить», она отменяет правку (§7). В отчёте — краткая строка отличий.

### 5.8 Общие настройки — страница «Настройки»

На странице показан конфиг: источники (включён ли, уровень, сайты, условия НДС и доставки) и правила (пороги, ставка НДС, индексация, текст методики). Внизу — поле, где агенту пишут, что поменять. Это отдельный агент — агент настроек — со своей историей и инструментами (§6.5); он работает только с общими настройками.

| # | Примеры | Что меняется |
|---|---|---|
| Н1 | «Добавь komus.ru в магазины», «Убери ozon.ru» | `sources.<id>.sites` |
| Н2 | «У Комуса бесплатная доставка юрлицам по МО от 5 000 ₽, вот страница условий: <ссылка>» | `site_delivery` / `delivery` источника; `note` — откуда условие (слова пользователя или ссылка). Условий, которых пользователь не назвал, агент не придумывает |
| Н3 | «Выключи Ozon», «Включи ГИСП», «Маркетплейсы — на первый уровень» | `sources.<id>.enabled`, `level` |
| Н4 | «Порог разброса 25 %», «Ставка НДС 20 %», «Индексируй цены старше 3 месяцев» | `rules.*` |
| Н5 | «Мы работаем по 223-ФЗ, вот формулировка из положения о закупке: …» | `rules.methodology_note`; в карточке — текст целиком |
| Н6 | «Что значит iqr_k?», «Какие источники включены?» | Ничего: ответ по конфигу |
| Н7 | «Что менялось?», «Отмени последнее изменение» | Журнал изменений; отмена |

- **Подтверждение — всегда.** Карточка «было → стало» и строка «Действует на новые закупки и на новые поиски. Посчитанные закупки не изменятся — в них можно попросить „пересчитай по новым общим настройкам“» → «Применить» / «Отмена». Как и в закупке, применить словами можно только в следующем ходе (§6.4).
- **Проверка — кодом.** Изменённый конфиг валидируется моделями `Rules` и `SourceConfig`; неверное значение — ошибка инструмента. Менять можно все поля `Rules` и у источников `enabled`, `level`, `params.sites`, `delivery`, `site_delivery`, `vat_default`, `vat_note`; добавить можно источник типа `web` (список сайтов или суффикс запроса). Источник нового типа требует нового адаптера в коде — агент так и отвечает.
- **Журнал** — `config_changes(id, created_at, path, before, after, reason, status)`. «Отменить» возвращает прежнее значение; если поле с тех пор менялось ещё раз — через подтверждение.
- **Где хранится.** Конфиг лежит в Docker-томе (`/data/config`); при первом запуске туда копируются значения по умолчанию из образа. Правки переживают перезапуск и пересборку. *(наше решение)*
- **Как доходит до закупок.** Правила и ИПЦ фиксируются в закупке при первом прогоне (§6.1), поэтому изменение общих правил начатые закупки не меняет — до просьбы Пр7. Источники не фиксируются: каждый новый поиск в любой закупке берёт текущие общие источники с учётом её локальных настроек; уже найденные предложения от этого не меняются.

## 6. Устройство

### 6.1 Данные

**База закупки.** При первом прогоне в закупке сохраняются общие правила, таблица ИПЦ и дата расчёта `calc_date`. Общие настройки потом могут меняться — на начатые закупки это не влияет. Правила закупки = база + локальные настройки (правки `local_setting`); базу обновляет только Пр7 (правка `rebase_settings`), дату расчёта — только С7. Так одни и те же данные и правки дают ту же цену и через неделю. *(наше решение)*

**Источники для поиска** не фиксируются: новый поиск берёт текущие общие источники и применяет к ним локальные настройки закупки (`enabled`, `sites`).

**Результаты поиска** — `ResearchRun`, одна запись на запуск поиска по позиции:
- `kind`: `full` (первый прогон, С4, С7), `targeted` (С1–С3), `user` (П5, П6);
- найденные предложения `FoundOffer(offer: Offer, policy: SourcePolicy, comparison: list[CharComparison])`, где `SourcePolicy(vat_default, vat_note, delivery: DeliveryPolicy)` — условия источника для URL предложения на момент поиска;
- страницы без цены (`SkippedPage`) и статусы источников (`SourceRun`).

Нормализация и расчёт в результатах поиска не хранятся: они пересчитываются при каждой сборке, потому что зависят от позиции и правил, которые пользователь может поменять.

**Набор результатов версии.** Каждая версия хранит `run_ids` — из каких результатов поиска она собрана. Новая версия берёт набор предыдущей и меняет его: `full` по позиции заменяет все её результаты, кроме `user`; `targeted` и `user` добавляются; отмена правки `add_offer` убирает её `user`-результат.

**Правки** — `Edit`:
```
Edit(id, procurement_id, seq, created_at, kind, position_index | None, target | None,
     payload (типизирован по kind), reason, reason_kind, origin: "chat" | "button",
     message_id | None, status: "active" | "cancelled" | "superseded")
```
`seq` задаёт порядок применения. `reason_kind` — у исключений: `characteristics | source | date | supplier | price | other` (§6.10).

**Предложения на подтверждение** — `Proposal(id, procurement_id, created_at, edit, preview: VersionDiff, status: "pending" | "applied" | "rejected" | "expired", turn_id)`.

**Версии** — как в плане (`report_versions`), плюс `edit_ids` (действующие правки) и `run_ids`. Старые версии никогда не меняются.

### 6.2 Сборка отчёта

`build_report(snapshot, parsed_tz, runs, edits, version, cause) -> Report` — чистая функция без сети и LLM. Заменяет `recalculate_position` из плана. `research_position` больше не считает итог, а возвращает `ResearchRun`; решение о подключении уровня 2 он принимает, вызывая `build_position` на данных уровня 1 с действующими правками (если пользователь уже исключил предложения, каскад это учтёт).

Порядок по каждой позиции:

1. **Позиция** = позиция из ТЗ → правки `answer_question` (сохранённая позиция) и `edit_position` по `seq`.
2. **Правила** = база закупки (с учётом `rebase_settings`) → правки `local_setting` для `rules.*`.
3. **Предложения** = `FoundOffer` из набора результатов версии → `dedupe` → дубли `duplicate`.
4. **`correct_offer`**: исправленные поля подставляются в `Offer`; исходные значения — в `OfferEntry.original`.
5. **Сопоставление**: сохранённое `comparison` с пометками существенности из шага 1 → `decide` (код) → `incomparable` / `insufficient_data`.
6. **Приведение цены**: `normalize_price`, `resolve_vat`, `index_price`, `resolve_delivery`, `adjusted_price` — с позицией из шага 1, `SourcePolicy` предложения, `calc_date` и ИПЦ из базы закупки → `unit_mismatch`.
7. **`include`**: предложение идёт в выборку в обход шага 5 и отбора по поставщику (только допустимые причины, §5.2).
8. **`exclude`, `exclude_where`** → `user_excluded` с причиной правки; предложения из источников и сайтов, отключённых локально (`local_setting` для `sources.*`), → `user_excluded` с причиной «источник отключён в настройках закупки».
9. `pick_per_supplier` → выбросы → `calculate` → `spread_hints` — как в плане.
10. **`exclude_position`** → позиция не входит в итог.

Затем `assemble_report` — как в плане, плюс раздел правок и предупреждения из §5.5 и §6.10.

**Конфликты.** Новая правка того же вида к той же цели переводит старую в `superseded` в момент создания: `exclude`/`include` к одному предложению; `correct_offer` к одному полю одного предложения; `edit_position` к одному полю; `local_setting` к одному ключу; `answer_question` к одному вопросу.

**Неприменимая правка** (предложение не нашлось при новом поиске) остаётся действующей и показывается в отчёте «не применена: предложение не найдено при поиске от <дата>». Если предложение найдётся снова (тот же `offer_id`), правка применится.

**`offer_id` не зависит от цены.** В плане `Offer.id = sha1(url + title + price)`: если цена на странице изменится между поисками, у предложения будет новый id и правка пользователя («исключи, там б/у») потеряется. Поэтому `Offer.id = sha1(канонический URL + title.casefold() + amount + amount_unit)[:12]` — фасовки на одной странице различаются, а смена цены id не меняет. Канонический URL — как в `dedupe`. *(наше решение)*

**Отмена и вытеснение правок, требовавших поиска.** Если отменяется (или вытесняется) правка `answer_question` или `edit_position`, после которой был новый поиск, и восстановленная позиция отличается по названию или значениям характеристик, — по позиции тоже запускается новый поиск: найденное под отменённую формулировку с позицией уже не сопоставимо. *(наше решение)*

### 6.3 Виды правок

| `kind` | `payload` | Шаг сборки | Откуда |
|---|---|---|---|
| `exclude` | `offer_id` | 8 | П1, кнопка в таблице |
| `exclude_where` | `position_index` (нет — все позиции), `filter: OfferFilter` | 8 | П2, С6 — через подтверждение |
| `include` | `offer_id` | 7 | П3 |
| `correct_offer` | `offer_id`, `field`, `value` | 4 | П4 |
| `add_offer` | `run_id` (результат `user`) | 3 | П5, П6 |
| `answer_question` | `question_id`, `answer`, `position` (результат `apply_answer`) | 1 | Р1, кнопка вопроса |
| `edit_position` | `field`: `quantity` / `essential:<имя>` / `characteristic:<имя>` / `name`, `value` | 1 | Р2–Р4 |
| `exclude_position` | — | 10 | Р5 |
| `local_setting` | `key` (`rules.<имя>`, `sources.<id>.enabled`, `sources.<id>.sites`), `value` | 2, 8 | Пр1–Пр6 — через подтверждение |
| `rebase_settings` | новая база: правила и ИПЦ из общих настроек | 2 | Пр7 — через подтверждение |

`OfferFilter` — условия через «И»: `source_ids`, `levels`, `price_date_before`, `price_date_after`, `normalized_price_above`, `normalized_price_below`, `vat_status`, `delivery_status`, `supplier`. Применяется кодом. Ценовые условия допустимы только вместе с `position_index`: у позиций разные единицы, «дороже 400» для всех сразу смысла не имеет.

`correct_offer.field` — `price`, `amount`, `amount_unit`, `vat`, `vat_rate`, `delivery`, `delivery_cost`, `delivery_free_from`, `price_date`, `supplier`, `supplier_inn`. Значение проверяет код теми же функциями, что и при извлечении (`parse_price`, единицы, ИНН из 10 или 12 цифр, ставка НДС 0–0,3). Неверное значение — ошибка инструмента, правка не создаётся.

### 6.4 Подтверждение

**Когда:** `local_setting`, `rebase_settings`, `exclude_where`, `revert_to_version`, С7, любые действия, которые агент предложил сам (В8), и все изменения общих настроек (§5.8). Остальное — сразу. Подтверждение нужно для просьб словами; кнопки в интерфейсе («Сбросить», «Пересчитать по общим», «Отменить») действуют сразу — нажатие однозначно, а результат виден в карточке версии с «Отменить».

**Как:**
1. Агент вызывает инструмент. Для этих видов код не сохраняет правку, а создаёт `Proposal`: собирает отчёт с этой правкой в памяти и считает `VersionDiff` с последней версией.
2. В чат публикуется карточка: что изменится («Для этой закупки: выброс — отклонение от медианы больше 25 % вместо 50 %») + разница («Позиция 3: 2 → 3 цены, станет обоснованной; итог 793 990 → 807 728 ₽») + кнопки «Применить» / «Отмена».
3. Применить можно кнопкой (`POST …/proposals/{id}/apply`, без LLM) или словами («да, применяй») — тогда агент вызывает `apply_proposal`. Код отказывает, если предложение создано в том же ходе агента: модель не может предложить и сама же подтвердить.
4. Любая новая версия переводит ожидающие предложения в `expired`: предпросмотр уже не верен. Агент при необходимости предлагает заново.

Поиск, запущенный в ходе, даёт свою версию позже. Кнопки без LLM (отмена правки, ответ на вопрос) — тоже одна версия на нажатие. *(наше решение)*

Текст ошибки подсказывает следующий шаг: для выброса — «можно предложить изменить правило выбросов».

### 6.6 Контекст агента и ссылки на предложения

На каждом ходе агент получает:
- системный промпт: принципы §3, когда нужно подтверждение (§6.4), отказы (§5.7, §6.10), «числа — только из результатов инструментов»;
- историю чата;
- краткую сводку последней версии и номер версии, которую пользователь сейчас смотрит;
- действующие правки, неотвеченные вопросы, ожидающие подтверждения `Proposal` (id и текст — чтобы «да, применяй» превратилось в `apply_proposal`), состояние прогона.

**Сводка.** По позиции — статус, цена за единицу, n, CV. По предложению — одна строка: метка, `offer_id`, источник и короткое название (как в таблице отчёта), расчётная цена, включено или причина исключения, пометки «НДС неизвестен», «доставка неизвестна», «исправлено / добавлено пользователем». Подробности — через `get_offer` и `get_position`.

**Как пользователь называет предложения:** «третье», «контракт 3810», «Регион», «самое дорогое». Чтобы «третье» значило одно и то же для человека и агента, у строк таблиц отчёта есть номер `<позиция>.<строка>` (включённые, затем исключённые, в порядке данных отчёта), и сводка использует те же метки. *(наше решение; в макете номеров строк пока нет)* Если под описание подходит несколько предложений, агент переспрашивает с вариантами: «Два предложения Регион: SvetoCopy (290 ₽) и SvetoCopy Eco (264 ₽). Какое?»

**Старая версия на экране.** Правки всегда вносятся в последнюю версию. Если пользователь смотрит не последнюю, агент говорит: «Правка внесена в последнюю версию (5); вы смотрели версию 3».

### 6.7 Карточка версии и ответ агента

После каждой новой версии код публикует в чат карточку (событие `report` с `VersionDiff`):

```
Версия 5 · Исключено: ЕИС, контракт № 3810…0007 — «поставка б/у»
Позиция 1: 310,98 → 304,10 ₽ за пачку (5 → 4 цены)
Итог: 793 990,00 → 776 790,00 ₽                    Показать · Отменить
```

«Отменить» — `cancel_edit` для правок этой версии. Текст агента рядом — одна-две фразы о смысле изменения; числа, если нужны, — только из карточки.

`VersionDiff` (код): итог до и после; по позициям — статус, цена за единицу, n, CV до и после; предложения, перешедшие между включёнными и исключёнными, с причиной; добавленные и отменённые правки; изменённые правила. Используется и для предпросмотра (§6.4), и для `diff_versions`.

### 6.8 Правки во время поиска

Поиск идёт в фоне, чат доступен всё время.
- **Вопросы** — по последней готовой версии; агент говорит, по каким позициям поиск ещё идёт.
- **Правки** сохраняются сразу. Если версия уже есть — сразу новая версия по имеющимся данным. Когда поиск закончится, его версия собирается со всеми действующими на тот момент правками, поэтому правка не теряется, даже если относится к позиции, по которой идёт поиск.
- **До первой версии** (например, ответ на уточняющий вопрос, пока идёт первый прогон) правка сохраняется и применяется при сборке первой версии. Если ответ требует нового поиска по позиции (§5.3, Р1), он запускается после окончания текущего поиска по ней.
- **Сборка и сохранение версии** — под блокировкой на закупку (`asyncio.Lock`), чтобы номера версий и набор правок не перемешались.
- **Повторный запрос поиска** по позиции, где поиск уже идёт, второй не запускает; агент сообщает состояние.

### 6.9 Версии и откат

- Переключение версии в панели — только просмотр.
- `cancel_edit` → правка `cancelled` → новая версия.
- `revert_to_version(k)`: действующими становятся правки и набор результатов поиска версии k; новая версия совпадает с версией k по содержанию (номер — следующий, `cause` — «Возврат к версии k»). Повторно в сеть не идём.

### 6.10 Подгонка

- Агент не исключает предложения по своей инициативе. Он может назвать вероятную причину разброса (подсказки уже есть в отчёте) и предложить действие; выполняет его только после подтверждения.
- Пользователь может исключить любое предложение с причиной — решение за ним (основная спецификация §5.6).
- **Исключение по цене видно в отчёте.** *(наше решение)* Правка считается ценовой, если у `exclude_where` есть ценовое условие или у `exclude` `reason_kind = price`. Агент ставит `price`, когда кроме цены или желаемого результата («дорогое», «чтобы прошёл разброс») причины нет. В отчёте у таких предложений пометка «исключено по цене», в предупреждениях: «Позиция N: пользователь исключил K предложений по цене — выборка сужена вручную».
- «Сделай цену X» — отказ всегда (Х1).

## 7. Что видит пользователь

**Чат**
- Карточка версии (§6.7) после каждой новой версии.
- Карточка подтверждения (§6.4) с «Применить» / «Отмена».
- Уточняющие вопросы с кнопками — как в макете; нажатие — `answer_question` без LLM.
- «Пропустить источник» — `skip_source` без LLM.

**Отчёт**
- Новый свёрнутый раздел «Правки пользователя» (как «Исключённые предложения»): что изменено, причина, версия, «Отменить»; неприменённые — с пояснением.
- В таблицах предложений: номер строки (§6.6); пометки «исправлено вами» (было → стало при раскрытии), «добавлено вами», «исключено вами: <причина>», «исключено по цене», «возвращено вами».
- В расчёте — строка «Настройки этой закупки отличаются от общих: порог разброса 40 % (общий 33 %); Ozon отключён» со ссылкой на вкладку «Локальные настройки». Предупреждения из §5.5 и §6.10.
- Кнопка версии в шапке — список версий с `cause`.

**Вкладка «Локальные настройки»** — третья вкладка правой панели рядом с «Отчётом» и «Браузером» (решение команды 2026-11-14; место — наше предложение). Настройки видны рядом с чатом, в котором их меняют.

```
 Отчёт   Браузер   Локальные настройки 2
 ──────────────────────────────────────────────────────────────
 Действуют только в этой закупке. Изменить — сообщением агенту.

 ┌ Общие настройки изменились после первого прогона:          ┐
 │ порог разброса 33 % → 25 %.          [Пересчитать по общим] │
 └────────────────────────────────────────────────────────────┘

 Расчёт
   Порог разброса (CV)       40 %   общий 33 %       [Сбросить]
   Минимум цен               3
   Выброс при < 5 ценах      отклонение от медианы > 50 %
   Выброс при ≥ 5 ценах      вне 1,5 × межквартильного размаха
   Ставка НДС                22 %
   Индексация                цены старше 6 мес.

 Источники
   ЕИС Закупки           уровень 1   включён
   Каталоги поставщиков  уровень 1   включён
   Магазины              уровень 2   komus.ru, vseinstrumenti.ru,
                                     market.yandex.ru
                                     ozon.ru отключён,
                                     в общих включён  [Сбросить]
```

- Показаны все настройки, которые можно менять локально (белый список §5.5), в действующих значениях. Изменённые выделены, рядом — общее значение и «Сбросить».
- Число на вкладке — сколько настроек изменено; без изменений число не показывается.
- «Сбросить» — отмена правки `local_setting` (`POST …/edits/{edit_id}/cancel`) сразу, без подтверждения: нажатие однозначно (§3, п. 4). Появляется новая версия, в чате — её карточка с разницей и «Отменить». Сброс отключения источника возвращает его предложения в выборку.
- Плашка «Общие настройки изменились после первого прогона» — если база закупки отличается от текущих общих настроек; перечисляет отличия. «Пересчитать по общим» — `rebase_settings` сразу (`POST …/settings/rebase`), тоже с карточкой версии и «Отменить».
- Менять значения в самом окне нельзя — только сообщением в чате: правки идут одним путём, с подтверждением и предпросмотром. *(наше решение; поля ввода в окне — возможное развитие)*
- Вкладка видна всегда, даже без изменений: так пользователь узнаёт, по каким правилам считается закупка.

**Страница «Настройки»**
- Конфиг в читаемом виде: источники (уровень, включён, сайты, условия НДС и доставки) и правила (с пояснением, что значит каждое).
- Внизу — поле для агента настроек; над ним — его история, карточки «было → стало» с «Применить» / «Отмена».
- Журнал изменений с «Отменить».
- Ключ OpenRouter и модель — как в основной спецификации.

**DOCX** — раздел «Правки пользователя» после «Исключённых предложений»; локальные настройки — в разделе «Расчёт»; те же пометки в таблицах.

Вид карточек и раздела делает команда в макетах.

## 8. API и модели

Дополнение к Task 12:
- `POST /procurements/{id}/messages` `{"text": str, "viewing_version"?: int}`.
- `GET /procurements/{id}/edits` → список правок.
- `POST /procurements/{id}/edits/{edit_id}/cancel` → `202`; новая версия — событием `report`.
- `POST /procurements/{id}/proposals/{proposal_id}/apply` и `…/reject`.
- `POST /procurements/{id}/questions/{question_id}/answer` `{"answer": str}` — кнопки вопросов.
- `POST /procurements/{id}/sources/{source_id}/skip`.
- `GET /procurements/{id}/reports/{a}/diff/{b}` → `VersionDiff`.
- `GET /procurements/{id}/settings` → для вкладки «Локальные настройки»: действующие значения из белого списка; у изменённых — общее значение и `edit_id` для «Сбросить»; отличия базы закупки от текущих общих настроек.
- `POST /procurements/{id}/settings/rebase` → `202`; кнопка «Пересчитать по общим».
- События SSE: `report {version, cause, diff}`, `proposal {id, text, diff, status}`; остальные — как в плане.

Общие настройки:
- `GET /config` → источники и правила; `GET /config/changes` → журнал.
- `POST /config/messages` `{"text": str}` → `202`; ответ агента настроек — событиями `GET /config/events` (SSE: `message`, `proposal`, `config`).
- `POST /config/proposals/{proposal_id}/apply` и `…/reject`; `POST /config/changes/{change_id}/cancel`.

Модели (дополнение к Task 1):
- Новые: `Edit` (payload — pydantic discriminated union по `kind`), `OfferFilter`, `Proposal`, `VersionDiff`, `AppliedEdit(edit, applied: bool, effect: str)`, `SourcePolicy`, `FoundOffer`, `ResearchRun`, `ConfigProposal`, `ConfigChange`.
- `Report`: `edits: list[AppliedEdit]`, `rules: dict` (действующие правила), `local_settings: list[str]` (чем настройки закупки отличаются от общих, человекочитаемо).
- `OfferEntry`: `label: str` («1.3»), `original: dict | None`, `user_marks: list[Literal["corrected", "added", "excluded", "excluded_by_price", "included"]]`.
- `PositionReport`: `excluded_by_user: bool`; `overrides` удаляется — его заменяют правки.
- `Report.questions[].answer` заполняется из действующих правок `answer_question` — тесты Task 13 на это опираются.

## 9. Примеры диалогов

На данных макета бумаги; цены условные.

**Вопрос (В2).**
> Почему исключили контракт 3810?

Агент вызывает `get_offer`: «Цена 412,00 ₽ за пачку выше верхней границы коридора 355,66 ₽. При 6 ценах выбросы ищутся по межквартильному размаху: всё, что вне [Q1 − 1,5·IQR; Q3 + 1,5·IQR], исключается.» Версия не меняется.

**Исправление (П4).**
> У «Северной бумаги» цена с НДС, это написано в шапке прайса.

`correct_offer(offer_id, "vat", "included", "в шапке прайса: «цены с НДС»")` → карточка «Версия 4 · Исправлено: НДС у «Северная бумага» — с НДС». Цена не меняется (множитель и так был 1), но из предупреждений уходит «НДС не подтверждён у 1 из 5». Агент: «Поправил, НДС по этому предложению теперь подтверждён, предупреждение снято».

**Массовое исключение (П2).**
> Оставь по позиции 2 только ЕИС.

`exclude_where(2, {source_ids: [web_suppliers, web_shops]}, "только контракты ЕИС")` → карточка подтверждения: «Исключу 1 предложение — Дистрибьютор «Регион». Останется 2 цены ЕИС, меньше 3: позиция 2 станет необоснованной, итог не посчитается. Применить · Отмена». Предпросмотр показал последствие до того, как человек согласился.

**Подгонка (Х1).**
> Сделай итог 750 тысяч.

«Итог — сумма по позициям, а цена позиции — среднее по найденным ценам; задать его напрямую нельзя. Больше всего в итог даёт позиция 1 — 777 450 ₽, там 5 цен от 290 до 329 ₽. Если какое-то предложение не подходит по сути, скажите — исключу с причиной. Могу поискать ещё цены.»

**Правило (Пр1).**
> Выбросом считай отклонение больше 25 %.

`change_local_setting("rules.median_max_deviation", 0.25)` → карточка: «Для этой закупки: при числе цен меньше 5 выброс — отклонение от медианы больше 25 % (сейчас 50 %). Правило для 5 и более цен (межквартильный размах) не меняется. Расчёт не изменится. Применить · Отмена».

**Ответ на вопрос словами (Р1).**
> Считай за 100 мкг.

`answer_question("q2-1", "За 100 мкг")` → `apply_answer` меняет `basis.per_tz_unit` на 100 → изменилась только база сравнения → пересчёт без поиска → карточка версии с новыми ценами за единицу.

**Отмена (Вр1).**
> Верни как было.

Последняя версия создана одной правкой (исключение контракта 3810) → `cancel_edit` → версия 6. Если последних правок несколько — `revert_to_version` с подтверждением.

**Общие настройки (Н1, Н2)** — поле внизу страницы «Настройки».
> Добавь komus.ru в магазины. Доставка юрлицам по Московской области бесплатно от 5 000 ₽, условия тут: <ссылка>.

`propose_config_change([{path: "sources.web_shops.params.sites", value: [..., "komus.ru"]}, {path: "sources.web_shops.site_delivery.komus.ru", value: {free_from: 5000, note: "<ссылка>"}}])` → карточка: «Магазины: + komus.ru. Доставка Комус: бесплатно от 5 000 ₽ (по условиям: <ссылка>). Действует на новые закупки и новые поиски. Применить · Отмена».

**Локальный источник (Пр5)** — в чате закупки.
> Не учитывай Ozon в этой закупке.

`change_local_setting("sources.web_shops.sites", [без ozon.ru])` → карточка: «Для этой закупки: Ozon отключён. Исключу 2 найденных предложения по позиции 3; останется 2 цены — меньше 3, позиция станет необоснованной. Общие настройки не меняются. Применить · Отмена».

## 12. Проверка

**Код** (pytest, без сети):
- правка переживает `rerun_position`, если то же `offer_id` найдено снова;
- правка к исчезнувшему предложению — «не применена»; при повторном появлении — применяется;
- `exclude_where` по источнику исключает и предложения из последующего `search_more`;
- `correct_offer(amount)` пересчитывает цену за единицу; исходное значение — в `original`;
- `edit_position.quantity` меняет доставку на единицу и итог без сети;
- более поздняя правка вытесняет раннюю (`exclude` → `include`);
- `include` для `anomalous_price`, `duplicate`, `unit_mismatch` — ошибка инструмента, версия не создаётся;
- `apply_proposal` в том же ходе, где создано предложение, — отказ; новая версия делает предложение `expired`;
- `revert_to_version(k)` даёт те же числа, что версия k;
- двойная сборка из тех же данных и правок даёт одинаковый отчёт;
- исключение по цене и правило мягче рекомендаций — предупреждения в отчёте;
- изменение общих правил не меняет начатую закупку; после `rebase_settings` — меняет, локальные настройки остаются поверх;
- локально отключённый источник: его предложения исключены с причиной, новый поиск его не вызывает, в общем конфиге он включён;
- `propose_config_change` с неизвестным ключом или неверным значением — ошибка, конфиг не меняется; `apply_config_proposal` в том же ходе — отказ;
- изменённый конфиг читается после перезапуска приложения (лежит в томе).

**Агент** (FakeLLM): по тесту на инструмент, как в Task 13.

**Набор фраз** (`backend/tests/agent_phrases.yaml`, маркер `live`, только с ключом): фразы из §5 → ожидаемый инструмент, «без инструмента» или «отказ». Прогоняется на выбранной модели OpenRouter перед демо и показывает, какие формулировки агент понимает неправильно.
