# Поиск и первый отчёт: этап 2

Ветка: `agents/backend-search`, зависит от завершённого `agents/backend-core`.
API закупок, БД, исполнение чат-инструментов и DOCX остаются этапу 3.

## Путь данных

1. `parse_tz.parse_tz(llm, text) → ParsedTZ`: позиции, характеристики, база цены,
   вопросы с уже применёнными ответами по умолчанию, доставка и дополнительные
   работы. Индексы и ссылки вопросов валидируются; ID вопросов назначает код.
   Для пачки бумаги база — одна пачка, не 500 листов. Если модель пропустила
   вопрос об аналогах для существенных марки/производителя/модели, код добавляет
   его с ответом «Нет, только …». `apply_answer` возвращает новую позицию.
2. `sources.registry.build_adapters`: включённые источники по уровням. Локальные
   `enabled/sites` накладываются на копии, общий конфиг не изменяется.
3. `research_position(..., snapshot, procurement_id=...) → ResearchRun`:
   источники одного уровня вызываются параллельно; страницы извлекаются и
   сопоставляются; исходные предложения и условия источников сохраняются отдельно
   от отчёта. Не более трёх позиций исследуются одновременно, запросы ЕИС —
   не более двух на адаптер.
4. `build_position(position, runs, snapshot, edits)` решает, достаточно ли
   уровня 1 после приведения, отбора по поставщикам и выбросов. При нехватке цен
   или неоднородности включается уровень 2, если он настроен. Учитываются
   действующие исключения пользователя. Объединённая выборка считается заново.
5. `run_research → ResearchResult(report, runs)`: возвращает и отчёт, и исходные
   результаты для будущего хранилища. События `progress`, `question`, `report`
   передаются через `Emit`; вопросы не блокируют поиск.

Сетевые адаптеры возвращают `SourceResult(pages, run, skipped)`; ошибка отдельного
источника не прерывает остальные. Ошибка извлечения/сопоставления одной страницы
попадает в `skipped_pages`; исходное предложение при ошибке сравнения сохраняется
с неподтверждёнными характеристиками, а не автоматически включается.

## Источники

`fetch` ограничивает тело HTTP-ответа 5 МиБ, текст обычной страницы — правилом
`page_text_limit`, таймаут — 20 секунд. Для сетевых ошибок, 429 и 5xx до трёх
попыток. Скрипты, стили и навигационная оболочка не поступают в LLM. Явная капча
или ограничение доступа отображаются как `needs_login`; пустая/нечитаемая
страница не считается предложением. При перенаправлениях проверяется URL;
локальные адреса и схемы кроме HTTP/HTTPS отклоняются.

`OpenRouterWebSearch` использует документированный web-плагин с движком Exa.
Ссылки берутся только из `url_citation`, а не из сгенерированного текста ответа.
`WebSource` добавляет до трёх существенных характеристик, суффикс источника и
`site:` для заданных доменов. Ограничение сайтов проверяется и после redirect.

ЕИС:

- Поиск по коротким `search_terms`, словоформам, 44-ФЗ и завершённому исполнению,
  без фильтра ОКПД2. Глубина `eis_years` проверяется локально по дате заключения:
  параметр `contractDateFrom` найден в HTML, но его формат в реальном запросе
  пока не подтверждён, поэтому он не угадывается.
- Читаются общая информация, объекты закупки, до десяти ссылок КТРУ и вкладка
  исполнения. Цена берётся из колонки «Цена за единицу», не из суммы контракта.
  Код также фиксирует единицу строки и НДС. LLM обязана указать номер строки;
  количество поставленных пачек не может стать делителем цены за одну пачку.
- Значения полных характеристик КТРУ привязываются к своей строке. При их наличии
  они заменяют извлечённые моделью значения; сравнение с требованиями остаётся
  задачей LLM. Для массы внутри штуки фасовка извлекается из описания.
- Неустойки проверяются по соответствующему столбцу таблицы. Любое значение
  кроме явного «Нет» исключает контракт. Если проверить не удалось, это явно
  отмечается. Отказ КТРУ/исполнения не теряет контракт; отказ основных вкладок
  сохраняется как пропуск. Карточка другого контракта отклоняется.
- В HTTP-клиент добавлен официальный Russian Trusted Root CA только для
  `https://zakupki.gov.ru`; проверка TLS не отключается. Источник, отпечаток и
  срок — в `backend/app/certs/README.md`. Системное хранилище не меняется.
  Chromium появится на P1 и потребует этого CA в своём отдельном профиле ЕИС.

## Извлечение и идентичность предложения

LLM извлекает цену и условия без расчёта. Код разбирает Decimal, фасовку, единицы,
ИНН, ставку НДС и дату. Неверная цена/фасовка становится пропуском с причиной.
Неверные необязательные доставка, ИНН и ставка не подменяются догадками.

`compare` возвращает значения предложения и оценку, но существенность и требуемое
значение всегда берутся из позиции. Пропущенная характеристика получает `ok=null`.
`decide`: существенное противоречие → `incomparable`; нет подтверждённых
существенных характеристик → `insufficient_data`; иначе предложение сопоставимо.

ID = SHA-1(канонический URL, название без учёта регистра, количество фасовки,
каноническая единица), первые 12 символов. Цена в ID не входит.

Уточнение старого плана: из URL удаляются tracking-параметры и fragment, но
сохраняются идентифицирующие параметры (`reestrNumber`, `contractSubjectId`,
`id`, `product_id`, `sku`, `variant`, `offerId`). Удаление всей query склеило бы
разные контракты ЕИС. При дедупликации учитываются название/фасовка и поставщик;
несколько строк одного контракта и одинаковая цена разных магазинов не теряются.

## Чистая пересборка

`build_report(snapshot, parsed_tz, runs, edits, version, cause, *, procurement_id,
created_at) → Report` не обращается к сети, LLM, файлам или текущему времени.
Если `created_at` не передан, он выводится из дат результатов/правок; без них —
из даты расчёта. Одинаковые аргументы дают одинаковый JSON.

`snapshot` фиксирует дату, правила и ИПЦ. Для позиции: исходные предложения →
дедупликация → исправленные поля → сохранённое сравнение с действующими
требованиями → приведение цены → ручной include/exclude → одна цена поставщика
→ выбросы → статистика. Нормализация выполняется и для несопоставимых предложений.
Изменённое требование не наследует старое «подходит». Исходные данные не меняются.

В сборщике поддержаны данные правок P0: `exclude`, `include`, `correct_offer`,
`answer_question`, их активность и порядок `seq`. Исходные значения и отметки
показываются в строках. Пропавшая цель — неприменённая правка; при повторном
появлении того же ID она применяется. Ручной include обходит сопоставление и
отбор по поставщику, но не несовместимые единицы, дубли или выбросы.
Создание/отмена правок через инструменты, сохранение и версии — этап 3.

Итог закупки доступен только при обоснованности всех позиций; частичная сумма
попадает в `total_justified`. Предупреждения показывают недостаток/разброс цен,
неизвестные НДС/доставку, отсутствие или неполноту ИПЦ, дополнительные работы
при поставке, ошибки источников и исключения по цене.

## Проверочный запуск

Из корня репозитория с `OPENROUTER_API_KEY` в `.env`:

```bash
uv run --project backend --locked python -m app.pipeline.preview \
  'backend/tests/fixtures/ТЗ поставка бумаги.docx' \
  --out data/paper --max-pages 3
```

Артефакты: разбор ТЗ `parsed.json`, база расчёта `snapshot.json`, результаты
`runs.json` с точными исходными ценами, публичный `report.json`. Секреты в них
не пишутся. `--parse-only`, `--parsed`, `--position` описаны в README;
`--timeout` ограничивает весь прогон (по умолчанию 900 секунд).

Обычный `make check` не использует ключ и сеть. Реальные HTML-файлы для
воспроизводимых тестов лежат в `backend/tests/fixtures/eis/`; там же происхождение
и SHA-256 оригиналов. Синтетические сценарии явно помечены в тестах и не выдаются
за результаты поиска. Живые ограничения записываются в маршрут бэкенда.
